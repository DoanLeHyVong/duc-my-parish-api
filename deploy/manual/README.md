# Native Ubuntu runtime (manual release only)

This directory supersedes `deploy/docker-compose.yml` for the owner's 1 GB VPS. The Compose files remain as historical rollback references; no workflow invokes them. Use `D:\AppGLV\_bmad-output\implementation-artifacts\ducmy-manual-vps-deployment-guide.md` for first installation, privilege setup, backup restore and release commands.

`main` CI produces a Linux x64 archive containing compiled `dist`, Prisma migrations/CLI and Node dependencies. Download it on Windows, verify SHA-256, then use `windows/Send-ApiRelease.ps1`. The VPS executes `api-release.sh --prepare` and `--release` only when an operator invokes them. No application build or test runs on VPS. Prepare creates a private SQL dump and manifest. `windows/Download-DbBackup.ps1` transfers it outside Git, verifies SHA-256 and sends a copy receipt. `restore-check.sh` verifies a disposable restore and writes proof. Release refuses Prisma migration until all evidence matches the same fresh dump. No Restic storage is required; Vultr Automatic Backups are a separate whole-VPS recovery layer.

Secrets belong in `/etc/ducmy` with mode 600/640, outside release directories. `api.env.example` is a field list, never a working credential file. The API listens on `127.0.0.1:5000` in production. Cloudinary stores uploaded images outside VPS; SQL backups do not include those images.

`restore-check.sh` creates a new `ducmy_restore_*` database, checks table/row counts and foreign-key orphans, and removes the disposable database after verification. It never replaces production. A Windows receipt is operator-produced evidence of a checked transfer, not an independent guarantee of later retention; protect and retain the Windows copy. The old `ducmy-backup.timer` must be disabled on VPS before replacing scripts. The new local prune script removes temporary SQL files after 48 hours. Application rollback changes a symlink only; it does not reverse Prisma migrations or restore a database automatically.
