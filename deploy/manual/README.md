# Native Ubuntu runtime and proof-gated API release

## GitHub Actions production preparation

`.github/workflows/deploy-production.yml` runs on `main` push or dispatch from `main`. It repeats Prisma validation, migration on a disposable CI database, lint, build, tests, archive and security checks before using SSH. Configure `VPS_HOST`, `VPS_USER` (`deploy`), `VPS_SSH_KEY`, and `VPS_KNOWN_HOSTS` as repository secrets; verify the VPS host key independently. Missing secrets fail before the first network call. The workflow compares the deployed API release, backup, restore and archive guard scripts by SHA-256 with the versions in Git and refuses preparation if any differs; install reviewed manual helpers separately before enabling.

The job uploads only the code archive and checksum, then runs `api-release.sh --prepare`. This creates the local private SQL dump but **does not migrate or restart** the API. The Actions run ending with `Backup prepared` is **PREPARED**, not production deployed. The operator must use the existing `windows/Download-DbBackup.ps1` outside Git, verify the Windows copy, run the disposable `restore-check.sh`, and then explicitly invoke `api-release.sh --release` with the same archive/checksum. The release script refuses mismatched or missing copy receipt/restore proof. Migration failure leaves the current code; if code rollback follows a successful migration, the schema is not rolled back. Inspect compatibility before retrying or rolling back. Never place plaintext SQL in GitHub artifacts or substitute a confirmation string for evidence.

Full API auto-deployment would require approved independent off-VPS encrypted storage, upload credentials scoped to it, confirmed retention, checksum and restore proof produced without trusting the VPS copy, and a reviewed change to the release gate. None is configured here. Vultr whole-VPS backup alone cannot prove a separate SQL copy. The existing `ci.yml` remains CI-only. The current workflow does not use Docker, seed, `db push`, or `migrate reset`.

This directory supersedes `deploy/docker-compose.yml` for the owner's 1 GB VPS. The Compose files remain as historical references; no workflow invokes them. Use `D:\AppGLV\_bmad-output\implementation-artifacts\ducmy-manual-vps-deployment-guide.md` for first installation, privilege setup, backup restore and release commands.

`main` verification produces a Linux x64 archive containing compiled `dist`, Prisma migrations/CLI and Node dependencies. The production workflow uploads it and invokes `api-release.sh --prepare` only. An operator completes `--release` after the independent Windows copy and disposable restore. The older Windows artifact path via `windows/Send-ApiRelease.ps1` remains available for recovery. No application build or test runs on VPS. Prepare creates a private SQL dump and manifest. `windows/Download-DbBackup.ps1` transfers it outside Git, verifies SHA-256 and sends a copy receipt. `restore-check.sh` verifies a disposable restore and writes proof. Release refuses Prisma migration until all evidence matches the same fresh dump. No Restic storage is required; Vultr Automatic Backups are a separate whole-VPS recovery layer.

Secrets belong in `/etc/ducmy` with mode 600/640, outside release directories. `api.env.example` is a field list, never a working credential file. The API listens on `127.0.0.1:5000` in production. Cloudinary stores uploaded images outside VPS; SQL backups do not include those images.

`restore-check.sh` creates a new `ducmy_restore_*` database, checks table/row counts and foreign-key orphans, and removes the disposable database after verification. It never replaces production. A Windows receipt is operator-produced evidence of a checked transfer, not an independent guarantee of later retention; protect and retain the Windows copy. The old `ducmy-backup.timer` must be disabled on VPS before replacing scripts. The new local prune script removes temporary SQL files after 48 hours. Application rollback changes a symlink only; it does not reverse Prisma migrations or restore a database automatically.
